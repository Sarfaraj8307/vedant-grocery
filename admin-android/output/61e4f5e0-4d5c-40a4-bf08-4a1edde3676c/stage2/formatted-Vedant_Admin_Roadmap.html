1. Executive summary

Vedant Fruit & Vegetables is a two-app system sharing one Supabase backend: a customer storefront (a Next.js Progressive Web App) and a store-owner operations app (a native Android application). This report covers the Android admin app, the subject of this implementation cycle, and closes with the forward roadmap for the customer web app.

What was built. The Android admin app is a complete, single-module Kotlin + Jetpack Compose application that lets the store owner operate the business from a phone instead of by phone call. It supports: server-enforced admin sign-in, working the order queue through its lifecycle, rejecting and restoring line items, managing the catalogue (products, categories, weight variants, offers, images), managing delivery slots, answering customer complaints, editing store settings, and viewing the administrator's identity.

Where it stands. All 29 capabilities defined in the PRD are implemented against the live backend contract, and the build is green: 410 JVM tests across 37 suites, 0 failures, a debug APK of 23,831,166 bytes, and 0 lint errors.

However — and this is the central message of this report — the live server paths and the on-device behaviours have not been executed, because the environment has no admin credentials and no device. The app is therefore built and unit-proven, but not yet live-proven.

2. What was delivered

The following capability areas are implemented in the admin app. Each maps to PRD capabilities and implementing tasks, and each is unit-tested against fakes (see section 7 for the exact verification status of each).

Order operations — the P0 core

  • An authenticated orders list with status filtering, search, and pull-to-refresh.
  • Order detail showing items, quantities, weights, per-line totals, adjustments, and the server-authoritative final total.
  • A status workflow driven by a validated state machine; the UI offers only the transitions the server permits, and the rendered status changes only after the server confirms.
  • Reject / restore an individual line item, with a required reason; totals are recomputed server-side and re-fetched, never computed on the device.

Catalogue management

  • A catalogue hub with a product list and an availability toggle that moves only after the server confirms.
  • Product editor (create/edit), categories, weight variants, and offers.
  • Image upload to the product-images bucket with real byte progress and a server-confirmed public URL — the image is only "set" once the URL is on the row.

Delivery slots

  • Slot listing, editing, and a "generate recurring slots" action backed by the ensure_delivery_slots RPC.

Customer support

  • A complaints list and thread view, with admin replies and image attachments path-scoped to the uploader.

Store settings, profile and session

  • Store settings editing (with a store-name warning when the live value looks wrong).
  • Profile / session view, where the role badge reads the server-resolved is_admin() value, never a locally cached or client-asserted role.

Foundations that make the above honest

  • Authentication with an explicit sign-in screen and a not-authorized refusal screen.
  • Admin authorisation enforced entirely server-side (see section 6).
  • Error handling, loading / empty states, offline resilience, animations, scrolling, accessibility, and dark mode as cross-cutting concerns.
  • Automated testing (JVM and compile-only instrumented suites) and production documentation.

3. Architecture

The admin app is a single-module (:app) application using Kotlin + Jetpack Compose + Material 3, following an MVVM / unidirectional data flow (UDF) pattern with hand-rolled dependency injection.

The layered design. The layering is enforced by convention and by test rather than by a framework:

LayerResponsibility
PresentationCompose screens + ViewModels; immutable UiState; one-shot events.
DomainModels, use cases, business rules — no Android or Supabase imports.
DataRepositories, Supabase / PostgREST access, DataStore cache.
PlatformSupabase (PostgREST / Auth / Storage) + DataStore + WorkManager.

The data layer is the only place the Supabase SDK is touched, the domain layer is pure Kotlin, and no business logic lives in composables. The dual-column database logic (section 5) lives only in the data-layer DTOs and mappers — no ViewModel or composable ever references a raw legacy column name.

Dependency injection. The app uses a small hand-rolled container plus a ViewModel factory, with the Application class building the container at startup. This is described in the code as "the Hilt seam" — the single place where a DI framework could be introduced later without touching feature code.

Why Hilt, KSP and Room were deliberately rejected. This was a conscious engineering decision, not an omission:

  • Hilt + KSP and Room + KSP both require annotation processing via KSP, which the project brief forbids. The team chose to honour that constraint rather than introduce a build-time code-generation step.
  • With a single module and a modest dependency graph, a hand-rolled container is simpler, faster to build, and fully transparent — there is no generated code to debug.
  • For persistence, DataStore Preferences was chosen over Room precisely because it needs no annotation processing. It stores the last-known JSON snapshots for the offline cache.
  • The only added build dependencies need no codegen: a settings library (session persistence), Coil 3 (image loading), DataStore Preferences (offline cache), WorkManager (safe-read retry), and Turbine (test-only Flow assertions).
  • Room, Hilt, KSP and the Realtime plugin were explicitly rejected; animations use native Compose rather than a third-party animation library.

Key project rules the architecture enforces: no business logic in composables, no Supabase calls from the UI, never fake success, money is server-authoritative, and admin authorisation is server-side only.

4. The live database is the authority

The single most important engineering finding of this cycle is this:

  All three prior schema documents were stale. The live database won.

Three separate sources disagreed with the live database, and each was treated as historical rather than authoritative once the live schema was read directly:

  • docs/BACKEND_CONTRACT.md — describes a different, older Supabase project; the live project is hyibaljxicojfoxbihdn. It is superseded and flagged to the owner as a follow-up.
  • PROJECT_INDEX.md — its schema and "nothing exists yet" claims were stale.
  • HANDOVER.md — likewise stale on both schema and project state.

The team resolved this by reading the schema out of the live database itself (via PostgREST with the publishable key), and by making docs/CONTRACT.md the single authoritative contract, with the explicit rule: where this file and any other document disagree, this file wins. The machine-checkable companion is docs/SCHEMA_SNAPSHOT.md.

22 recorded doc-vs-live conflicts (C1–C22). Each is a case where a document said X and the live database said Y. At summary level:

SourceConflictsRepresentative examples
docs/BACKEND_CONTRACT.md11 (C1–C11)Wrong project ref; an order-status enum using retired values; complaints status IN_REVIEW vs the live IN_PROGRESS; under-specified column lists; two live surfaces (store_settings, product_catalog view) not documented at all; missing storage path rules.
PROJECT_INDEX.md7 (C12–C18)"No Android code exists yet", "design system not yet created", "no libraries added yet", "no screens implemented", "storage has 0 policies → uploads fail" — all contradicted by the live repo and database.

The lesson recorded for the future team: a hand-maintained type or contract file drifts silently; always reconcile against the live source before trusting a column. The customer PWA's own hand-maintained database type file is the next instance of this same drift (see section 12).

5. Legacy column pairs

The live database carries six paired-column traps, each a newer "intended" column shadowed by a legacy duplicate. The admin app handles every one of them with a documented, per-pair policy that lives only in the data layer. The policy has two parts: the read column (the one the mapper consumes) with its fallback, and the write policy (what an admin save does).

The six legacy / duplicate column pairs and their exact policy
#Intended / authoritativeLegacy duplicateReadFallbackWrite policy
1products.base_priceproducts.pricebase_pricepriceWrite both, same value
2products.quantity_limitproducts.max_order_qtyquantity_limitmax_order_qtyWrite both, same value
3delivery_slots.capacitydelivery_slots.max_orderscapacitymax_ordersWrite both, same value
4delivery_slots.starts_at / ends_at (timestamptz)delivery_slots.start_time / end_time (time)starts_at / ends_atstart_time / end_timeWrite both — starts_at/ends_at as UTC timestamptz; start_time/end_time as the Asia/Kolkata wall-clock derived from them
5categories.glyph + categories.accentcategories.icon (+ slug)glyph (visual) + accent (colour)iconWrite glyph + accent AND slug; mirror icon := glyph
6orders.delivery_slot_idorders.slot_iddelivery_slot_idslot_idN/A — read-preferred with a read-only fallback; the admin app never writes an order row

Pair-by-pair rationale (in brief).

  • Pairs 1–4 (write-both). For products and slots, the safe strategy is to keep both columns equal, so that whichever column the server ultimately charges or counts from sees the administrator's value. Pair 1 matters because place_order prices from least(price, discount_price) — so price is genuinely read by the server. Pair 4 is the type-correct case: starts_at/ends_at are timestamptz (authoritative, keyed by the slot-recurrence unique index), while start_time/end_time are time.
  • Pair 4 detail. start_time/end_time are the Asia/Kolkata wall-clock rendering of the same instants that starts_at/ends_at hold in UTC.
  • Pair 5 (evidence-based). The customer storefront renders glyph + accent and never reads icon or slug; the live icon column is empty for two categories and wrong for a third.
  • Pair 5 write policy. An admin category save writes the authoritative glyph + accent (and slug for URL hygiene), and mirrors icon := glyph so no surface ever renders a blank.
  • Pair 6 — the corrected one. orders.delivery_slot_id versus orders.slot_id is read-preferred with a read-only fallback — it is NOT a write-both pair. This distinction was corrected once already during the cycle and the corrected policy is what is implemented.
  • Pair 6 behaviour. The mapper prefers delivery_slot_id and falls back to slot_id only when the former is absent. There is no write half, because the admin app never writes an order row — it only reads orders and calls admin_update_order_status.

  Tally: 6 of 6 pairs resolved. No pair is genuinely open. The one outstanding probe (to confirm which column admin_slot_load reads for capacity, pair 3) is non-blocking, because pair 3 is written identically either way, so the ambiguity is harmless regardless of the answer.

6. Security and money invariants

Three invariants are enforced throughout the app. They are the reason the app can be trusted not to leak a secret, not to over-grant access, and not to mis-state an amount.

Invariant 1 — only the publishable key ever enters the APK

The Supabase publishable (anon) key is the only credential compiled into the application. No service-role key exists anywhere in the app — a dedicated security-hygiene test (7 assertions) exists to fail the build if a privileged key were ever introduced. The "publishable key is public by design" model relies on Row-Level Security, not on the key being secret.

Invariant 2 — admin authorisation is server-side and never cached locally

Every admin capability is gated by the server's private.is_admin() function, called through the is_admin() RPC. The app never decides authorisation itself and never caches a role assertion locally — the profile screen's role badge reads the server-resolved is_admin() value, not a value from profiles.role.

A non-admin who signs in correctly is shown a not-authorized refusal screen with no admin data rendered; the refusal comes from the server's gate, not from client logic. Every admin RPC is SECURITY DEFINER and raises 42501 for a non-admin.

Invariant 3 — money is server-authoritative; the client never sends an amount

The client never transmits a price, a discount, or a total. When an administrator rejects or restores a line item, the app sends only the item and a reason; the server recomputes the totals and the app re-fetches the row and displays the server's values. Money is represented internally as integer minor units to avoid floating-point drift, but that representation is used only for display — the authoritative figure is always the one the server returns.

The database's own CHECK constraints (for example adjustment_amount <= 0) are the final guard: because the client never sends an amount, a malformed amount is structurally impossible to submit.

Cross-cutting. Two further rules reinforce the three invariants: "never fake success" — a mutation's result is rendered only after the server confirms it — and storage path discipline — a complaint image must be uploaded under a key prefixed with the uploader's user id, because the storage policy authorises by the first path segment.

7. Verification status

This is the honest three-way split. Each of the 29 PRD capabilities carries exactly one status:

  • VERIFIED — executed and observed, with the proof.
  • IMPLEMENTED-BUT-UNVERIFIED — the code exists and is covered against fakes (unit tests); the live-server or hardware path that would prove it end-to-end is blocked.
  • BLOCKED — cannot be verified in this environment; what is needed to unblock it is stated.

What each category means in practice. The 8 VERIFIED items are those provable without the live server or hardware: error taxonomy and copy, UI state scaffolding, offline/caching logic, dark-mode contrast logic, JVM test execution, and documentation. Several are marked "logic" precisely because their physical half — real offline behaviour on a device, real on-screen appearance — remains blocked.

What would move the needle. Clearing R1 converts the order, catalogue, slots, support and settings capabilities from IMPLEMENTED-BUT-UNVERIFIED to VERIFIED by executing the end-to-end plan. Clearing R2 converts the animations, accessibility and the instrumented half of testing, plus the physical half of dark mode.

Clearing both converts the end-to-end capability. Until then, no capability that depends on the live server or on hardware is VERIFIED, and this report says so.

9. Known gaps and unimplemented items

This section is deliberately forthright. These are the things that are not done or not proven.

  • Dashboard count tiles are not wired. The dashboard shell renders, and the backing dashboardCounts() function exists — but the count tiles are not yet connected to it. This is a real, recorded defect. The dashboard capability is therefore IMPLEMENTED-BUT-UNVERIFIED with this additional caveat.
  • The instrumented (Compose UI) test suites have never been executed. All 9 androidTest files compile, but none has run on a device or emulator (R2). There is no on-device evidence for any screen.
  • All live RPC paths are unverified. Every admin operation that calls a server function — signing in, the is_admin() gate, status transitions, item reject/restore, catalogue writes, image upload, slot generation, complaint writes, settings saves — has been exercised only against fakes. None has been run against the live backend.
  • Not yet proven on real hardware: real offline behaviour, real accessibility (screen-reader traversal, focus order, touch-target sizes on a physical screen), animation behaviour, and the physical appearance of dark mode.
  • The RLS-hidden table columns remain un-enumerated. Because there are no admin credentials (R1), the column lists of the twelve RLS-hidden tables (orders, order_items, profiles, complaints and others) could not be read. They have been left explicitly UNKNOWN rather than guessed; a probe script is committed to resolve them when credentials exist.
  • One non-blocking database probe is outstanding — confirming which column admin_slot_load reads for slot capacity (harmless pending, because the value is written to both columns identically).

11. Owner decisions pending

One data-quality item needs the owner's decision.

categories.accent appears to hold placeholder colours. The live categories table stores a numeric accent value per category, and the sampled values are pure RGB primaries: 16711680 (= #FF0000, pure red) and 65280 (= #00FF00, pure green). These look like placeholder data rather than a considered brand palette. The team deliberately left these values unchanged, pending the owner's decision, because:

  1. Changing production catalogue data on the owner's behalf would be overstepping.
  2. The correct brand colours are a business decision, not an engineering one.

Action needed: the owner should review the category accent colours in the admin app's category editor and set them to the intended brand palette. No code change is required — the editor already writes accent correctly (it is part of the authoritative pair-5 write, section 5).

Related owner-visible data issues surfaced during the cycle:

  • store_settings.store_name reads "Fresh Mart" — wrong for a store branded Vedant Fruit & Vegetables. The admin app warns on this value but deliberately does not silently rewrite it; the owner should correct it via the settings screen.
  • Several customer-facing store settings on the live project (phone, whatsapp) are empty, which hides the corresponding contact affordances on the storefront until filled in.

12. Customer web app roadmap

The customer storefront is a separate application — a Next.js Progressive Web App — that shares only the backend contract with the admin app. This section summarises its forward plan, distilling the full technical handoff in docs/CUSTOMER_WEB_APP_HANDOFF.md. Every item is clearly separated into already implemented versus recommended future enhancement.

12.1 Already implemented (customer web app)

The storefront is a live, mobile-first PWA with a real functional surface today:

  • Catalogue & browsing — browse by category, free-text search, offers-only and in-stock-only filters, and sorting by name or price.
  • Weight variants — the store's differentiator: a product can be bought in multiple weights, each with its own price.
  • Cart — persisted locally and merged into the server cart on sign-in, so a basket survives a refresh or a PWA relaunch.
  • Checkout — address and delivery-slot selection, with a money preview that mirrors the server's arithmetic, and a confirmation screen showing the server's returned totals.
  • Orders — order history and order detail with live status and a status timeline.
  • Delivery tracking — a status tracker; DELIVERED and CANCELLED are terminal.
  • Customer support — complaints list and thread, with database-enforced rules (a customer cannot self-resolve a complaint).
  • Accounts — sign-up, sign-in, sign-out, password reset, address book, and an account overview.
  • PWA features — installable, with a service worker, an offline fallback page, and an update prompt.
  • SEO & structured data — per-page metadata, OpenGraph/Twitter cards, and local-business structured data.
  • Security — RLS as the security boundary; only the publishable key reaches the browser; the environment loader actively rejects a service-role key.

Also delivered and worth naming: the contract reconciliation worked out for the admin app (the six legacy pairs, section 5) is shared, and the storefront already reads the authoritative side of each pair.

12.2 Recommended future enhancement

Grouped by theme. Each is an idea, clearly not a claim of existing functionality.

  • Trust & identity (highest value, lowest risk — recommended first): correct the store name and supply the store's phone, WhatsApp, address and contact email so the Call/WhatsApp buttons and structured data activate; provide the 8 products that currently have no image (Beetroot, Capsicum (Green), Carrot, Cucumber, Grapes (Black), Lemon, Mint (Pudina), Potato) — doable directly from the admin app's image upload.
  • Contract & correctness: regenerate the storefront's hand-maintained database type file from the live schema (it is stale in exactly the way section 4 describes), then re-run its build/lint/type gates; fix a known hydration mismatch in the quantity-stepper component; remove a dead, unused dependency; consolidate a duplicated complaint service.
  • Engineering foundation: configure the declared-but-dormant unit-test stack and add a continuous-integration pipeline (types, lint, build, tests); put the database under version-controlled migrations; add analytics (the storefront currently has none).
  • Customer experience: order-status notifications (push, and/or the owner's preferred WhatsApp/SMS channel) written through the existing notification outbox; guest checkout; reorder-from-history; wishlist/favourites; a live delivery map/rider ETA.
  • Growth: sitemap and robots files, per-product structured data, category SEO copy, and a seasonal content hub.
  • Advanced: online payment (orders are paid on delivery today) and personalised recommendations.

12.3 Recommended top three

  1. Fix store identity & owner configuration — the store name, the four store-contact values, and the 8 missing product images. Business-visible, inexpensive, and it unblocks the Call/WhatsApp channels and structured data.
  2. Close the data-contract gap & fix the known defect — regenerate the database types from the live schema and fix the hydration mismatch, so the storefront and the admin app do not drift apart as they evolve.
  3. Build the engineering foundation — unit tests for the money/pricing/validation pure functions plus a CI pipeline, which makes every later change safe.
