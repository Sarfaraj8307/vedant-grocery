01Executive summary

A capable operations console. Its authority model is far more built than the app shows, and its analytics answer a moment rather than a direction.

What is strong. Order handling is complete and honest: the status machine, item rejection with server-computed money, and delivery runs all work against a server that is the single source of truth. The client never computes an amount it sends and never displays a change the server has not confirmed. The Compose UI has also been exercised on an emulator — 42 instrumented tests passed on 13 October — so this is not an untested drawing.

The headline finding. The database already implements a five-role authority model — OWNER, ADMIN, MANAGER, DELIVERY, SUPPORT — with a per-domain permission matrix. The Android app ignores all of it and gates on a single boolean, is_admin(), which is now a compatibility shim equal to "is any staff member". A staff management screen was built and then deliberately deleted on 20 October. The capability is not missing; it was removed.

What else is missing.

  • Analytics describe a moment, not a direction. Three fixed windows, a 100-row cap, no charts, no export, and no product, customer, or delivery axis.
  • No privileged operation has run against the real server. Every mutation is proven only against fakes, because no admin credentials exist. The emulator run is real but fake-backed.
  • The offline policy has no single definition. It is hand-applied in ten screens with two different standards, and one screen — the delivery workflow — has none.
  • Destructive actions are inconsistent. Deleting a category asks first; deleting an offer, a weight variant, or a slot does not.
The one sentence to carry into planning

The app is feature-complete for the shop floor and under-built for the owner: it tells a packer exactly what to do next, and it tells the person who owns the business almost nothing about how the business is doing — or who on staff did what.

03Full functionality inventory

Everything an administrator can do today, grouped by domain. "Write" changes server state; "Read" only displays.

3.1 Authentication & entry

Auth 3 screens

Splash · Sign in · Not authorized

  • Sign in with email + password (Supabase Auth). Double-submit blocked; in-flight state shown.
  • Session restore on cold start, with a retry path rather than a silent bounce to sign-in.
  • Server-side check on every launch; a signed-in non-staff user lands on a dead-end screen that reveals no data and offers only sign-out.
  • Sign out from the dashboard and the profile screen.

3.2 Home

Dashboard 1 screen

Dashboard

  • Today's numbers: today's order count and sales value.
  • Live pipeline: New / Packing / Ready / Out counts.
  • Eight destinations: Orders, Deliveries, Catalogue, Slots, Support, Reporting, Store settings, Order acceptance — the last carrying live open/closed state in its subtitle.
  • Identity: signed-in email, plus sign-out.

3.3 Orders & fulfilment

Orders 2 screens

Orders list · Order detail

  • Browse orders with status filter chips, debounced search, paging and pull-to-refresh.
  • Read an order as a receipt: status, customer, line items with weight and quantity, subtotal, delivery fee, adjustments, final total.
  • See delivery detail: customer, phone, slot, address; one-tap call via the dialler.
  • Follow the timeline of every status change with timestamps and reasons — but not who made the change (see §4.6).
  • Advance the status through the server-enforced machine: PENDING → CONFIRMED → PROCESSING → READY_FOR_DELIVERY → OUT_FOR_DELIVERY → DELIVERED.
  • Cancel an order from any non-terminal state — a reason is mandatory.
  • Reject a line item with a required reason; the server recomputes the bill. Restore a rejected item to undo it.
  • Raise a complaint against an order.

Delivery 1 screen

Delivery

  • Work a run: today's delivery orders, one card each.
  • Call or navigate to the customer.
  • Start delivery and mark delivered (status transitions).
  • Report an issue with a typed reason; the report becomes a complaint.

3.4 Catalogue

Catalogue 5 screens

Catalogue hub · Product editor · Categories · Weight variants · Offers

  • Browse and search products, filter by category and availability, page through results.
  • Toggle availability inline; the switch only moves once the server confirms.
  • Create or edit a product: name, description, glyph, category, base price, discount price, unit and unit label, stock flag, per-order limit.
  • Upload a product photo from camera or gallery, with real byte progress, retry on failure, down-sampling to 1600 px / JPEG 85. The photo is only "set" once the server-confirmed URL is on the row.
  • Control visibility: listed, available, featured.
  • Manage categories: create, rename, reorder, hide, delete (delete asks for confirmation).
  • Manage weight variants: label, grams, price, availability — inline edit and delete (delete is immediate).
  • Manage offers: title, discount percent, offer price, date range, enabled flag; labelled Active / Scheduled / Expired / Disabled (delete is immediate).

3.5 Delivery slots

Slots 1 screen

Delivery slots

  • Read the day schedule, grouped by date, with each slot's window and capacity.
  • See utilisation per slot — booked, places left, percentage, distinct treatment when full.
  • Generate recurring slots for a rolling horizon in one action.
  • Create, edit and delete individual slots (delete is immediate).

3.6 Customer support

Support 2 screens + 1 alias

Complaints list · Complaint thread · (Support — alias of the list)

  • Browse complaints with status filters, search and paging.
  • Read a thread as a conversation: customer left, store right, status events centred.

  • Move the complaint status through its own machine.

3.7 Settings & identity

Order acceptance · Store settings · Profile · Appearance

  • Resume taking orders in one tap.

  • See the role the server confirms, with a note that a stored role column is informational only.
  • Choose appearance: system default, light, or dark.
  • Sign out.

Analytics

04User handling & authorities

4.1 The app's gate is one boolean

The Android client knows exactly one question: is this user staff?

LayerMechanismConsequence
IdentitySupabase email + passwordAny signed-in user can attempt anything; the server decides.
The gate the app usesprivate.is_admin()Checked on the app's privileged calls and its launch gate.
What that actually meansis_admin() is a compatibility shim whose body is select private.is_staff();Any of the five staff roles passes it identically.
Client postureNever trusts a cached role; profile shows the server's answerA UI-only bypass gains nothing — but the boolean is coarse.
The authority finding, stated precisely

A fine-grained permission matrix exists in the database and the app does not use it. Because is_admin() now aliases is_staff(), a DELIVERY or SUPPORT account passes the same door as the owner. The client then renders every surface to them — catalogue editor, store settings, money fields — even where the server would refuse the write. The result is not a data breach; it is an app that shows people doors it will not open for them, and an owner who cannot tell which of their staff can do what.

4.2 What the server already implements

This is the part the report exists to surface. None of it is visible in the app.

This is a good design that the client contradicts

Read the matrix and it is exactly what a grocery needs: a support agent cannot touch the catalogue, a driver cannot change money, and only the owner can mint another owner. Somebody thought this through carefully. The app then asks one question instead of seven, and shows everyone the same twenty-one screens.

4.4 A staff screen was built, then deleted

Commit 0203028 (20 October) is titled "One-click order acceptance on dashboard; remove staff UI; demo accounts". Its body states that the staff screen, view-model, DTO, RPC methods and navigation wiring were removed, and that private.user_roles and owner_grant_role stay.

The reason is visible in the migrations: admin_list_admins() had its EXECUTE revoked from authenticated in migration 002 when it was superseded, so the staff screen had nothing to list. Migration 012 then added admin_list_staff() to restore that read. The read exists again; the screen does not.

Why this changes the recommendation

"Add role-based access control" is a quarter-long project. "Rebuild a screen you already built, against a roster read that now exists, on a matrix that is already enforced" is a week. The decision to remove it was a decision about an unreadable roster — and that reason no longer holds.

4.6 Accountability is captured and then discarded

Every status change records changed_by. That value is parsed at OrderStatusHistoryDto, mapped at OrderMapper, and carried on the domain model at Order.kt. It is then referenced by zero screen files.

The app knows who acted and never shows it. Displaying the actor is a one-line change in the timeline — the cheapest governance improvement available anywhere in this product — and it is the precondition for any staff-performance reporting later.

4.7 What restoring authority requires

  1. Read the role, not the boolean. Replace the client's is_admin() check with the caller's staff_role, and gate the UI on the same can_manage_* helpers the server already uses. The matrix needs no design work.
  2. Rebuild the staff screen against admin_list_staff(), with grant and revoke through owner_grant_role / owner_revoke_role. The last-OWNER guard already prevents locking the store out.
  3. Show the actor in the order timeline.
  4. Add a cross-order audit view. Every write flows through a named RPC, so the record exists; only the read surface is missing.
  5. Confirm the irreversible. Closing the store, cancelling a paid order and revoking access each complete in one tap today. Deleting an offer, weight variant or slot does too — while deleting a category asks first.

5.2 The structural verdict

Two axes, and both describe the present

The analytics have exactly two dimensions — time (three fixed windows) and status (the pipeline). Everything a grocery owner decides with is on a third and fourth axis that does not exist: what sold (product, category) and who bought (customer, repeat rate). The screen reports the shape of a day; it cannot report the direction of a business.

Three ceilings, all verified in source:

  • 100-row history cap — past that volume the totals and the visible rows describe different populations.
  • Fixed windows — Today, 7 days, 30 days. No custom range, no period-over-period, so seasonality and month-on-month growth are unanswerable.
  • Numbers, not charts — a deliberate early decision, right at the time, but a 30-day trend has to be read as thirty rows.

The most telling row

Seven of the eight missing axes need no new data collection. The timestamps, reasons, customers, slot loads and actor identity are already written on every order. The gap is a reporting gap, not a data-capture gap — which makes it far cheaper to close than it looks. One pattern explains three separate instances: capture is centralised and correct, surfacing is ad hoc.

The check certified a claim it did not test

This is the single most important finding in the review. OfflineGatingScreenTest exercises five screens — Catalogue hub, Categories, Offers, Weight variants and Slots. Its own doc comment claims "offline gating on every mutation surface", and the run record cites it as the T26 fix "verified for real, not against fakes".

It covers 5 of 11 mutation surfaces. The six it never touches are Order detail, Product editor, Store settings, Order acceptance, Complaint thread — and Delivery, the one screen with no gating at all. A green run on a 45% sample certified a universal claim, and the certification is what made the gap invisible.

To be precise about where the fault lies: the test itself is well written. For each of its five screens it asserts both halves of the standard — control disabled and reason shown. It is not a weak test. It is a correct test carrying an incorrect title, and the green result transferred credibility from the test to the claim. That is why four hint-less screens passed review: nothing in the run was false, only the scope stated in the name.

The real defect is the habit, not the five screens: the gating was applied by package rather than by policy. Catalogue and Slots got gate, hint and test; Orders, Settings and Support got the gate alone; Delivery, its own top-level package, got nothing. A task was closed where its author was looking, and the test inherited the task's title instead of its coverage.

7.3 Cheapest path to closing the biggest risk

One owner account, one device, one afternoon. Sign in, then walk the mutation surfaces once each — accept an order, reject an item, restore it, change a status, toggle a product, upload a photo, reply to a complaint, save a setting, close and reopen the store, then work one delivery with the radio off. That single pass converts most of this report from implemented to verified, and would have caught R1 before a driver did.

7.4 The pattern behind both halves of this report

The only variable is whether the policy had a name

is_admin() is one policy, with one definition, applied centrally — and it held for the entire build. Connectivity is one policy, with no definition, applied twelve times by hand — and it was already inconsistent within a single pass.

Same codebase, same team, same standard of care. The difference is not discipline: it is that one policy had a seam to hang on and the other had to be remembered at every call site. Every finding in §4 and §7 is an instance of that. Which is also why the fix is cheap: name the policy, and the call sites stop mattering.

08Appendix — method, evidence & corrections

Method. Three independent readings of the same capability inventory — maturity, structure, and risk — followed by direct source verification of every claim that reached this report. Where a lens and the code disagreed, the code won.

Verified directly in source:

  • 21 destinations, including the Support alias and the orphan Appearance entry.
  • public.staff_role enum and the can_manage_* matrix, read from the migrations; is_admin() defined as select private.is_staff();
  • Commit 0203028 removing the staff screen, view-model, DTO, RPC methods and navigation wiring.
  • admin_list_admins() EXECUTE revoked in migration 002; admin_list_staff() added in 012, gated on can_manage_roster().
  • changed_by parsed, mapped and modelled, with zero references in any screen file.
  • DeliveryScreen contains zero connectivity references; four write controls gated only on !busy.
  • Ten screens read LocalOnlineStatus; six render OfflineHint.
  • Delete confirmation: Categories has an AlertDialog; Offers, Weights and Slots have none.
  • is_open present on the store-settings update DTO as well as behind the acceptance RPC.
  • HISTORY_LIMIT = 100; no chart, canvas or export code in the analytics feature.
  • 465 unit tests; docs/INSTRUMENTED_TEST_RUN_2026-10-13.md records 42/42 green, while app/build/outputs/androidTest-results/ no longer exists.

Corrections applied during this review. Recorded because they change the argument, not the arithmetic:

  1. "No audit trail" → a per-order trail exists and renders. Narrowed to: the actor is captured and never displayed.
  2. "Roles were never attempted" → a staff UI was built and deliberately deleted on 20 October; the roster read was then restored server-side. The recommendation changed from "build RBAC" to "restore it".
  3. "Instrumented tests never ran" → they ran, 42/42, on 13 October. Corrected to "passed once, fake-backed, artifacts missing, and predating every subsequent change".
  4. "Uniform offline gating on nine surfaces" → ten screens, two standards, one screen with none.

Stated limits. This report reads the codebase, not the business. It cannot say whether sales, complaints or slot utilisation are improving — and neither can the app, which is the finding in §5. Figures such as the eight missing product images come from the project's own defect list and were not re-verified against the live database. The live database itself was not queried; the role model is read from migration files.
